# UX review 1: the first 20 seconds

Reviewed all 16 PNGs in `e2e/screenshots/` at their supplied viewport sizes, plus `docs/BUILD-NOTES.md`. I also checked the chart data shape and order entry implementation to make the fixes feasible. This is a screenshot and source review, not a live venue or browser test. The target reader is a daily Hyperliquid or Binance trader deciding quickly whether the venue deserves an order.

## 1. Ranked problems

1. **The main desktop chart looks broken.** In `01-live-1440x900.png`, center from x244 to x839 and y273 to y567, there are axes, a last-price box, and a TradingView mark but no visible history. The same void persists in `01-arrival-1440x900.png`, `03-funded-1440x900.png`, `01-resting-1440x900.png`, and `05-filled-rail-1440x900.png`. A trader reads this as a failed feed. `02-market-view-390x844.png` shows that a line can render on phone, so the desktop presentation needs a concrete fix before more decoration. The service schema already has open, high, low, close, and volume. Draw those real candles, fit the loaded range, and show a named loading or unavailable state if there are fewer than two valid points.
2. **Account state and the submit action are cut off by page height.** In `03-funded-1440x900.png` and `06-positions-1440x900.png`, the account dock begins at the bottom edge around y859 and its rows are not visible. In `02-open-orders-1440x900.png`, the selected `Open orders` tab is visible but the order itself is not. The faucet link sits outside the order card around y833; in `01-arrival-1440x900.png`, even the submit button is clipped. The broad blank band under the chart does not buy useful information. A daily trader must see positions, open orders, and the full order control without scrolling the page.
3. **Order entry announces failure before the trader acts, then lets an unaffordable order look placeable.** In `01-trade-view-390x844.png`, `01-arrival-1440x900.png`, and `01-resting-1440x900.png`, red `quantityRequired` or `limitPriceRequired` appears beneath untouched fields. In `01-rejected-1440x900.png`, the form shows `Available: 5,000.00 nUSD`, estimated initial margin `5,974.00 nUSD`, an enabled bright `Place test long` button, and only then an insufficient-balance rejection. Map validation codes to human language, defer required-field errors until interaction or submit, and disable or constrain an order that the local estimate already proves unaffordable. See section 3.
4. **The visible `Cancel order` control has unsafe scope.** `01-resting-1440x900.png` shows one order-specific cancel button; `02-open-orders-1440x900.png` implies an order-row action. Build notes say it actually calls `POST /v1/dev/cancel-all` for the market. That action can remove other resting orders. Hide the per-order cancel affordance until the venue has a true order ID route, or label and confirm the real scope as `Cancel all NSOL-PERP orders`. `03-cancelled-1440x900.png` then loses the order timeline and retains only `Click to confirmation: 16 ms`, so the result is hard to audit. Keep a `Cancelled` event, cancelled quantity, time, and order ID in the rail.
5. **The numbers disagree across surfaces.** In `05-filled-rail-1440x900.png`, the market list says `151.74`, the main mark says `151.57`, the chart last-price label says `151.76`, and the own fill is `151.59`. The fill may correctly differ from a mark, but the first three lack distinct timestamps and source labels to explain the gap. `03-recovered-1440x900.png` also returns to `Live` while the blank chart and old looking prices give no visible proof that the data was refreshed. Use one current mark snapshot for header, watchlist, and chart marker; label the fill as execution price; show each source time and stale state.
6. **The review dialog hides the actual order instruction.** In `04-confirm-first-order-1440x900.png`, the modal title says `Confirm Place test long`, but the body starts with `Quantity cost`; it does not clearly restate `NSOL-PERP`, `Market`, `Long 1 NSOL`, `1x cross`, or the maximum buy price `153.11 nUSD` shown behind it. `Est. liquidation 0.75` has no unit or visible method. The phrase `Do not ask again` sits next to material risk data. Make the first line a compact exact order sentence, show the protective bound and unit, then cost, fee, margin, and estimate provenance. The button can remain `Place test long`.
7. **Speed reads as marketing because its measurement context is buried or absent.** In `01-live-1440x900.png` and `01-rejected-1440x900.png`, the `Venue pulse` card shows p50 and p99 with 40 orders, but no rolling window or `TEST NETWORK` beside the number. Its long methodology text consumes most of the 260 px card. In `01-resting-1440x900.png`, an individual `16 ms` appears next to venue p50 `264 ms` without an immediate explanation that they are different clocks and cohorts. Use a compact line such as `TEST NETWORK · Confirm p50 264 ms · p99 479 ms · n=41 · last 15 min`, an updated age, and a `How measured` detail control. Label the personal metric `This device, click to venue response`; retain accepted and rejected in the definition. Do not show a fresh-looking number when the measurement window is stale.
8. **Privacy proof is hidden below the fold and the public tag weakens the anonymous story.** In `01-public-view-raw-1440x900.png`, the raw response begins below y850; the visible card mostly repeats a generic Public/Only you list and a `127.0.0.1` URL. More seriously, build notes say every order's browser-generated `clientTag` is echoed on public tape rows. That lets public observers link fills carrying the same tag, even if they cannot see balances or resting orders. `05-filled-rail-1440x900.png` marks one tape row `yours`, but the public correlator must be disclosed and reviewed before calling public fills anonymous. The public view should show a compact checked time, unsigned request source, response excerpt, and explicit list of fields returned, including `tag`; put full raw JSON in a bounded inspector. Claim only that the inspected unsigned endpoint omits account state at that check time.
9. **The right rail spends prime space on prose while hiding tradable context.** In `02-wallet-created-1440x900.png`, the pulse's paragraph and the public view's two narrow prose columns occupy much of x856 to x1116; the witness rail says only `Your orders appear here`. In `01-resting-1440x900.png`, `1.0 at 1.00` does not state unit, side, order type, or that `1.00` is the limit price versus the current 149.90 mark. Show `Long 1 NSOL · Limit 1.00 nUSD`, remaining size, age, and cancel scope. Collapse methodology and raw schema text behind details controls. The rail should earn its place beside the chart.
10. **The first minute is visually repetitive and poorly sequenced.** `01-arrival-1440x900.png` and `01-trade-view-390x844.png` each show `Create test wallet` twice. In `02-wallet-created-1440x900.png`, `Get 5,000 test USD` is an underlined link below the order form and near or beyond the viewport edge. In `03-funded-1440x900.png`, the same faucet link still competes with trading. Keep one primary contextual action in the order panel: wallet creation, then test funding, then order placement. Put recovery information beside creation; move repeat funding to the wallet menu after the first grant.
11. **The phone does not deliver a 20 second trading read.** In `01-trade-view-390x844.png`, header, intro, and a 192 px three-row market switcher push the quantity field to y626 and the submit action below the screenshot. In `02-market-view-390x844.png`, the chart finally shows movement, but the tape and witness rail are further down. Keep one compact market selector and a 52 px sticky market bar; show mark, change, side/type, quantity, and action in the first viewport. Let `Trade` and `Market` switch full content views without repeating the large market list.
12. **The disconnected state is too easy to miss.** In `02-connection-lost-1440x900.png`, only the small top-right dot and `Connection lost` text change; the chart still shows a price box and `just now`. `03-recovered-1440x900.png` returns to `Live` with no refreshed-at marker or visible reconciliation result. Freeze the chart with a `Market data paused · last update HH:mm:ss` overlay, mark estimates stale, and make the order button say why it is disabled. On recovery, show `Account and market refreshed at HH:mm:ss` only after both have actually completed.

The test simulator and invented route shapes in build notes are integration assumptions. Do not ship the visual promises of protected market execution, per-order cancellation, or risk-engine liquidation until the real venue contract confirms them. The current client-side liquidation estimate uses a flat maintenance assumption; its exact value should never read as an authoritative liquidation threshold.

The four workspace columns are 176 + 700 + 212 + 296 px, separated by three 8 px gaps; 16 + 176 + 8 + 700 + 8 + 212 + 8 + 296 + 16 = 1440. ## 3. Order entry: exact changes

**Field order.** Fixed header `Trade NSOL-PERP · TEST NETWORK`, followed by mode if a market supports both `Spot | Perps`; otherwise show the actual mode as a label. Next: `Long | Short` for perps or `Buy | Sell` for spot; `Market | Limit` only when the venue supports each; `Available` with collateral and unit; `Quantity` with unit and `Max` or percentage shortcuts constrained by fee and margin; then `Execution limit` for a protected market order or `Limit price` for a limit order. For perps, put `Leverage` with numeric value and allowed range after price, then `Cross margin` as a mode label and `Reduce only` only when a position can be reduced. Finish with `Estimated notional`, fee, initial margin, liquidation estimate with method and timestamp, remaining available balance, and one primary action. Spot omits leverage and liquidation and shows maximum spend or minimum proceeds when enforceable. Never show an executable market control until the service confirms it honors the protection bound.

**Before any input.** No red text. Quantity is blank with a quiet hint like `Min 0.01 NSOL · step 0.01`; price bound is prefilled only if it is a real supported instruction, labelled `Max buy price 153.11 nUSD` or `Min sell price ...`, with `1.0% from mark` and mark age. Summary rows say `Enter quantity to see estimate` once, not `Unavailable` four times. The initial primary button is disabled and reads `Enter quantity`; after wallet creation with zero funds it reads `Get 5,000 test nUSD`; with a valid funded order it reads `Place test long` or the actual side. Remove the second global wallet CTA and the persistent faucet link below the panel. A review dialog, when used, repeats exact side, quantity, market, type, bound, collateral, fee, and risk in that order.

**Errors.** Validate on blur or attempted submit, then update live. Replace `quantityRequired` with `Enter a quantity in NSOL.` and `limitPriceRequired` with `Enter a limit price in nUSD.` Put the message under the relevant field, connect it with `aria-describedby`, and focus the first invalid field on submit. Other exact examples: `Minimum order is 0.01 NSOL.`; `Use increments of 0.01 NSOL.`; `Maximum buy price must be above the current mark.`; `Available 5,000.00 nUSD; this order needs about 5,979.97 nUSD including fee. Reduce quantity or leverage.`; `Market data is 8 seconds old. Wait for a fresh mark.` Rejection text is distinct from local validation: `Venue rejected this order: insufficient collateral. No fill occurred.` Keep the attempted values for correction, and never leave an enabled submit button beside a known blocking error. For an unknown outcome, say `Checking this order with the venue. Do not resubmit yet.`

## 4. Chart minimum for a serious venue

Render the real OHLC candles already defined in the market data schema, with an aligned volume histogram from its `volume` field. Fit the initial 20 or more available candles to the visible 700 x 356 plot, leave useful right padding, and do not let a live mark update wipe or compress the series. A loaded chart needs legible time and price axes, interval selection, crosshair values for `O H L C V`, a clear last-mark line with timestamp, and public fill markers with a small legend. Show the selected market and interval over the plot. The chart's last-mark label and header must use the same current mark snapshot; a candle close may differ and should say `close` in the crosshair. If OHLC or volume is unavailable, draw the actual close series and explicitly label missing volume rather than inventing candles or bars. If data is loading, say `Loading 1m history`; if it fails, say `Price history unavailable · Retry` while retaining the last known mark and its age. A blank grid plus a last-price box is not an acceptable loaded state. Keep Lightweight Charts; no new chart dependency is needed.

## 5. Five changes with the largest polish return

1. **Make the data surface credible.** Fix initial desktop chart fitting, draw real candles and volume, synchronize the current mark across header/list/chart, and show data age. This is the first glance test.
2. **Lock the complete trading workspace into 900 px.** Use the dimensions above. Keep the order action and one full account table visible, with only bounded internal scrolling. Remove duplicate onboarding banners and unused vertical space.
3. **Rebuild the entry hierarchy.** Show available funds and a readable quantity prompt before errors; label the execution bound as a maximum or minimum price; present cost, fee, and risk before the action; pre-block unaffordable orders. Keep the first-order review precise.
4. **Make execution state exact.** The witness rail should name market, side, type, price unit, size, remaining size, and source of each event. Keep cancelled and rejected receipts visible. Give cancellation its actual scope, and resolve the venue API contract before showing order-specific controls.
5. **Turn claims into compact inspectable evidence.** Put p50/p99, sample count, rolling window, network, and last update on one line, with methodology on demand. Make the unsigned public response and exposed `tag` visible in a bounded inspector, and narrow privacy wording to what that response demonstrates.

These are UX priorities from the supplied captures. The screenshots do not establish that the real service accepts the invented order fields, enforces a protective bound, or returns the assumed public tag. Those contract points require service integration evidence before the interface can present them as venue guarantees.
